# 架构设计

## 一、设计目标与约束

| 目标 | 对应的设计决策 |
| --- | --- |
| **评审者能一键复现** | 运行时零第三方依赖；`npm install` 不下载任何包 |
| **断网环境可用** | 静态规则引擎完全离线；前端无 CDN 依赖；图表用 SVG 手绘 |
| **结论可审计** | 每条问题带判据来源；得分含完整扣分明细；记录携带代码指纹与计分参数 |
| **大模型失败不影响可用性** | 双引擎物理隔离，大模型相关阶段全部按「可选增强」实现，逐级降级 |
| **可横向扩展语言与规则** | 语言画像表驱动；规则为声明式数据，加载时校验字段合法性 |
| **无遗留技术债** | 不引入第三方包，因此不存在依赖升级与漏洞修补负担 |

## 二、分层结构

```text
┌──────────────────────────────────────────────────────────────┐
│  接入层    Web 评审台 · CLI · REST API · CI 门禁 · Gitee 集成  │
│            —— 只做协议适配，不含业务逻辑                        │
├──────────────────────────────────────────────────────────────┤
│  服务层    HTTP 微框架 · 评审服务 · 评分卡 · 报告导出 · 存储     │
│            —— 业务编排：校验 → 调度 → 融合 → 计分 → 持久化      │
├──────────────────────────────────────────────────────────────┤
│  引擎层    引擎 A 静态规则分析     ‖     引擎 B 大模型语义评审    │
│            —— 检出能力所在；两者物理隔离、可独立降级             │
├──────────────────────────────────────────────────────────────┤
│  支撑层    配置中心 · 日志 · 错误体系 · 分类字典 · 测试 · 容器化  │
│            —— 横切能力，被上层复用                              │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向严格自上而下**。接入层不直接依赖引擎层，必须经过服务层编排；
引擎层不感知 HTTP 与存储，只接收纯数据并返回纯数据。这保证了：

- 引擎可脱离服务独立测试（`static-analyzer.test.js` 直接调用引擎，不启动服务）；
- 服务层可在测试中以 mock 引擎替换（`review-service.test.js` 用 mock 大模型后端）；
- 接入形态可独立增加（新增 CI 集成不需要改动任何引擎代码）。

## 三、核心机制设计

### 3.1 三通道词法预处理

**问题**：纯正则方案面临两难——要检出字符串里的硬编码密钥，就必须看到字符串内容；
但看到字符串内容后，`const label = "a == b"` 这样的代码会被「松散相等」规则误报。

**方案**：把源码拆为三份**等长**文本。所有通道的长度、换行位置与字符偏移完全一致，
因此任意通道的命中结果都能精确映射回原始行。

| 通道 | 注释区 | 字符串区 | 实现方式 | 服务的规则类型 |
| --- | --- | --- | --- | --- |
| `code` | 空格替换 | **原样保留** | 单遍字符扫描 | 硬编码凭据、SQL 拼接（需要读取字面量） |
| `syntax` | 空格替换 | 空格替换 | 在 `code` 基础上二次扫描 | 松散相等、浮点比较、除零（只关心运算符结构） |
| `comment` | **原样保留** | 空格替换 | 与 `code` 同一次扫描产出 | TODO / FIXME 识别（只关心注释内容） |

**关键技术点**

- 换行符在三个通道中**始终保留**，这是行号对齐的前提；
- 字符串扫描需处理转义字符与跨行字面量（JS 模板字符串、Python 三引号），
  且普通字符串遇到换行必须视为提前闭合，否则一处未闭合引号会吞掉整个文件；
- Python 三引号字符串按注释统计（文档字符串的语义更接近注释）；
- 已知局限：正则字面量 `/.../` 与除号无法在纯词法层区分，形如 `a / b / c` 的表达式
  可能被保守地当作字符串处理。该偏差已被明确记录并在测试中固化。

### 3.2 声明式规则引擎

每条规则是一个纯数据对象，引擎按 `scan.type` 分派执行：

| 扫描类型 | 通道 | 适用规则 |
| --- | --- | --- |
| `line` | `code` | 硬编码凭据、SQL 拼接、明文 HTTP |
| `syntaxLine` | `syntax` | 松散相等、浮点比较、同步 IO、调试输出 |
| `rawLine` | 原始行 | 行尾空白（注释行也可能有） |
| `comment` | `comment` | TODO / FIXME |
| `custom` | 完整上下文 | 空 catch 块、除零守卫检查、循环内串行 await、度量阈值类规则 |

**加载期校验（fail fast）**：`rules/index.js` 在模块加载时逐条校验 `id` 唯一性、
`dimension` / `severity` 合法性、`scan` 结构完整性。任何规则写错都会在进程启动时
立刻抛错并指明是哪一条，而不是在运行期静默失效。

**噪声抑制**：

- 每条规则可设置 `maxPerFile`，避免同一类问题刷满报告；
- `filter(match, lineText, ctx)` 钩子支持上下文相关的排除逻辑
  （例如「除零」规则会回溯 6 行检查是否已有与 0 的比较或取反判断）；
- 结果按 `${ruleId}|${line}` 去重，同一规则同一行只保留一条。

### 3.3 大模型多角色编排

**为什么不一次调用问全部维度**：单次调用需要模型同时兼顾安全、性能、可读性、
正确性四个互不相关的目标时，注意力被稀释，结论容易泛化且遗漏。
四个角色各自持有独立的系统提示词与职责边界（明确要求「忽略不属于你的问题」），
结论的针对性与稳定性显著提升。

**编排要点**

| 机制 | 实现 |
| --- | --- |
| 分段送审 | 超过 `REVIEW_CHUNK_LINES` 时按行切块，并向 ±40 行范围内寻找空行作为切点，尽量保持函数与代码块完整 |
| 行号还原 | 每段携带全局起始行号，提示词中的代码按 `行号 \| 代码` 格式呈现，模型返回的行号会被夹取到该段合法区间 |
| 并发控制 | 自研 `mapWithConcurrency`，在「不触发服务端限流」与「不退化为串行」之间取平衡 |
| 避免重复报告 | 提示词中附带规则引擎已发现的问题摘要（行号 + 规则 + 标题），要求模型补充语义级问题而非重复 |
| 输出归一化 | 统一 JSON 契约；字段缺失或非法时按角色默认维度回退；标题、消息、建议均有长度上限 |

**输出契约**（四个角色统一，解析器只需一套实现）：

```json
{
  "summary": "一句话总体结论",
  "findings": [
    {
      "line": 12,
      "severity": "blocker | critical | major | minor | info",
      "dimension": "security | bug | performance | readability | maintainability",
      "title": "不超过 16 字的问题标题",
      "message": "问题描述：说明触发条件与可能后果",
      "suggestion": "可直接落地的修改建议",
      "confidence": 0.8
    }
  ]
}
```

### 3.4 双引擎结果融合

```text
规则引擎结论 ──┐
               ├──► 按 (维度相同 且 行号差 ≤ 2) 比对
大模型结论   ──┘         │
                        ├─ 命中：判定为「互相印证」，模型结论不重复计入，
                        │        规则结论的 confirmedBy 计数 +1
                        └─ 未命中：模型结论保留，计入 llmOnlyCount
```

**为什么以规则引擎结论为准**：规则结论是确定性的、可复现的、可指向具体判据的。
模型结论与之重合时，价值在于**提供独立证据支持该问题真实存在**，而非新增一条重复条目。
融合后的统计字段（`confirmedCount` / `llmOnlyCount`）为后续评估两路引擎的一致率提供了数据基础。

### 3.5 评分模型

```text
综合得分 = clamp(100 − σ × Σ(严重级别权重 × 来源可信度), 0, 100)
维度得分 = clamp(100 − σ × Σ(权重 × 可信度 × 维度敏感度), 0, 100)
```

| 因子 | 取值 | 设计意图 |
| --- | --- | --- |
| 严重级别权重 | 15 / 10 / 5 / 2 / 0.5 | 后果的不可逆程度决定权重；安全类问题权重最高 |
| 来源可信度 | 静态 1.00；大模型 0.80 × confidence | 确定性结论全额计分；概率性推断按置信度折算 |
| 规模归一化 σ | `1 / (1 + ln(max(N,30)/30)/3)` | 抑制「大文件因条目多被系统性低估」的偏差 |
| 维度敏感度 | 安全 1.20 · 缺陷 1.00 · 性能 0.90 · 可读 0.80 · 可维护 0.80 | 安全问题的修复成本随时间指数上升 |
| 结构风险修正 | 复杂度超 15、嵌套超 4 层时附加扣分 | 「复杂但暂时正确」是未来缺陷的温床，条目式计分无法体现 |

**为什么引入 σ**：若采用绝对扣分，一个 5000 行的遗留文件即使只有零星轻微问题，
也会因条目累积而得分极低，这与工程直觉不符。σ 使「同样 3 处缺陷出现在 1000 行代码中
比出现在 50 行代码中更可接受」这一判断被量化。σ 随规模单调下降且有上界 1，
行为已在单元测试中固化（`sizeNormalization` 单调性测试）。

### 3.6 降级策略矩阵

| 失败点 | 影响面 | 处理 |
| --- | --- | --- |
| 未配置大模型密钥 | 语义评审、修复建议、结论摘要 | 自动进入纯规则引擎模式；结论摘要改用确定性兜底结论；`warnings` 中说明 |
| 单个角色调用失败 | 该角色的结论 | 其余角色与规则引擎结果照常输出；`llm.errors` 记录原因（按错误信息去重后进 `warnings`） |
| 全部角色调用失败 | 全部模型结论 | **审查整体仍然成功**（HTTP 201），得分由规则引擎结论计算，绝不返回 5xx |
| 输出被 `max_tokens` 截断 | 该次调用 | 抛出携带 `finish_reason` 与推理 token 用量的精确诊断；该错误不重试（重试必然复现） |
| 单条规则抛异常 | 该规则 | 捕获后跳过并记录 warn 日志，其余 40 条规则照常执行 |
| 修复建议生成失败 | 修复建议 | 回退到 12 条内置修复模板，报告中标注来源为 `template` |
| 记录文件损坏 | 该条历史记录 | 构建索引时跳过并告警，不影响服务启动 |
| 端口被占用 | 服务启动 | 明确提示检查 `PORT` 并给出处理建议 |

**核心原则**：静态分析是可用性底线，任何大模型相关问题都不得使整体审查失败。

## 五、存储设计

**选择 JSON 文件而非数据库的理由**

| 维度 | JSON 文件 + 内存索引 | SQLite |
| --- | --- | --- |
| 依赖 | 无（内置 `fs`） | 需第三方包，破坏零依赖承诺 |
| 数据可读性 | 人可直接打开查看 | 需工具 |
| 归档与迁移 | 复制目录即可 | 需导出 |
| 万级以下记录性能 | 索引命中为内存 Map 查询，微秒级 | 相当 |
| 适用边界 | 本项目的团队级使用场景 | 十万级以上、并发写入场景 |

**可靠性设计**

- **原子写入**：先写 `<id>.json.<pid>.tmp`，再 `rename` 覆盖目标文件。
  `rename` 在同一文件系统上是原子操作，因此进程在任何时刻中断，磁盘上的文件都是完整 JSON。
- **崩溃恢复**：启动时扫描目录重建内存索引，无需额外的一致性修复步骤。
- **容错**：单条记录损坏时跳过并告警，不影响服务启动与其余记录的读取。

## 六、安全设计

| 风险 | 防护措施 |
| --- | --- |
| 密钥泄露 | `.env` 已在 `.gitignore` 中排除；`/api/meta/config` 只下发病钥掩码，响应体中不存在 `apiKey` 字段 |
| 路径穿越 | 静态资源路径解析后校验是否仍位于根目录之内，越界一律返回 404 |
| XSS（报告导出） | 所有用户内容在插入 HTML 前统一转义，已在测试中固化（含 `<script>` 注入用例） |
| 请求体过大 | `MAX_BODY_BYTES` 限制，超限立即销毁连接并返回 413，避免内存被持续占用 |
| 响应头注入 | 安全响应头集中设置：`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy` |
| 未捕获异常 | `unhandledRejection` 与 `uncaughtException` 统一捕获并记录，避免进程静默退出 |
| 日志泄露 | 日志中不打印密钥原文；异常堆栈仅在 `debug` 级别输出 |

**已知缺口（明确声明）**：本版本未内置接口鉴权。部署到公网前必须在反向代理层
加 Basic Auth 或 IP 白名单。

## 七、可扩展性

| 扩展方向 | 需要的改动 |
| --- | --- |
| 新增一种审查规则 | 在 `src/analyzers/rules/` 对应文件追加一个规则对象；无需修改引擎 |
| 新增一种语言 | 在 `languages.js` 的 `LANGUAGES` 表追加一条画像（扩展名、注释符号、字符串定界符、决策关键字） |
| 新增一个大模型角色 | 在 `prompt-templates.js` 的 `ROLES` 表追加角色定义；`review-agent` 会自动纳入调度 |
| 新增一种报告格式 | 在 `report-service.js` 增加 `toXxx()` 并在 `exportReport` 的分派表中注册 |
| 接入新的模型后端 | 若兼容 OpenAI 协议，只需配置 `LLM_PROVIDER=openai-compatible`；否则在 `llm-client` 增加分支 |
| 替换前端 | 后端仅暴露 REST 接口，前端可整体替换为 React / Vue 而无需改动服务端 |
| 接入 Git 平台 PR 审查 | 复用 `POST /api/reviews`，由平台 Webhook 触发即可 |
